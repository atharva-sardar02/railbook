RailBook: how the whole app runs

Six diagrams, from the big picture down to what happens when things fail. All names, ports and numbers are from the running system (verified 2026-10-24/25).

1. The map: everything that runs, and every port

Three layers: your laptop, Docker's kind network, and the Kubernetes cluster inside one Docker container. Only Kong (127.0.0.1:80) and Splunk's web UI (127.0.0.1:8000) are reachable from your browser. Every port is tagged with where it lives: [laptop], [container] (a Docker container on the laptop), [node] (opened on the kind node container), [service] (a stable in-cluster address) or [pod] (where the program really listens). The complete list is in section 7.

2. One booking, end to end

What happens when you press Pay & book. The request ID Kong adds is the thread that ties together every log line about this booking.

sequenceDiagram
  autonumber
  participant B as Browser
  participant K as Kong gateway
  participant S as Service railbook-api
  participant A as API pod (FastAPI)
  participant P as Postgres
  participant L as Logs → Splunk

  B->>K: POST /bookings (127.0.0.1:80)
  Note over K: Route "POST /bookings" picks these plugins:
correlation-id: add X-Request-ID (uuid)
rate-limiting: max 20 per minute per IP
prometheus: count + time it
file-log: write one JSON line
  alt over 20 bookings this minute
    K-->>B: 429 Too Many Requests (the API never sees it)
  else allowed
    K->>S: forward with X-Request-ID
    S->>A: to one Ready pod, port 8000
    Note over A: middleware binds request_id to every log line
pydantic checks the body (bad input → 422)
    A->>P: BEGIN · SELECT seats ... FOR UPDATE
    Note over P: Row lock: two people booking the same class
wait in line, so seats can never go negative
    alt not enough seats
      A-->>B: 409 "only N seats left"
    else payment declined (simulate failure ticked)
      A->>P: ROLLBACK (no seats taken)
      A-->>B: 402 "payment declined"
    else payment OK (mock provider, key from Vault)
      A->>P: seats = seats - N · INSERT booking (new 10-digit PNR) · COMMIT
      A-->>K: 201 + PNR + X-Request-ID
      K-->>B: 201 Confirmed, PNR shown
    end
  end
  A--)L: JSON lines: booking_confirmed, request (status, duration_ms, request_id)
  K--)L: JSON line: status, latency, x-request-id

3. An API pod starting: how it gets its secrets

No password is stored in the code, the image, Kubernetes Secrets or GitHub. Each pod proves who it is to Vault and gets its own database user, valid 1 hour and renewed while the pod runs.

sequenceDiagram
  autonumber
  participant K8s as Kubernetes
  participant I as Vault Agent Injector
  participant Init as vault-agent-init (init container)
  participant V as Vault
  participant P as Postgres
  participant App as api container
  participant Side as vault-agent (sidecar)

  K8s->>I: new pod has label vault-agent-inject=true (webhook fails closed)
+ annotation vault.hashicorp.com/agent-inject
  I-->>K8s: add an init container + a sidecar to the pod
  K8s->>Init: start first
  Init->>V: login with the pod's service account token (role railbook-api)
  V->>K8s: is this token real? (TokenReview)
  K8s-->>V: yes: account railbook-api, namespace railbook
  Init->>V: read database/creds/railbook-api + secret/railbook/payment
  V->>P: CREATE ROLE v-kubernet-railbook-... (1 h lease)
  V-->>Init: username, password, payment key
  Init->>Init: write /vault/secrets/app.env + db.json,
save token + leases to the shared cache, exit
  K8s->>App: start: load app.env into env vars, then python -m app
  Note over App: config from ConfigMap (DB_HOST, PORT ...)
+ payment key from app.env · DB user from db.json
(read on every new connection) · listens on :8000
  K8s->>App: readiness probe GET /readyz (pings the database)
  App-->>K8s: 200 ready → pod joins the Service, Kong starts sending traffic
  Side->>Side: start from the init container's cache (same lease, same DB user)
  loop while the pod runs
    Side->>V: renew the lease before the hour runs out
  end
  Side->>V: at max_ttl (24 h): read a new DB user
  Side->>Side: rewrite db.json → next DB connections use the new user

4. From code change to production

Nobody copies files to a server. A merged pull request is tested, scanned, built once and deployed automatically, with no downtime.

flowchart TD
  dev["You open a pull request"] --> prchecks["GitHub-hosted runner: checks
gitleaks (secrets) · ruff (lint)
11 tests on real Postgres 16 · helm lint"]
  prchecks --> review{"Checks pass and
you merge to main?"}
  review -- no --> dev
  review -- yes --> checks["checks job again on main"]
  checks --> image["image job (GitHub-hosted)
docker build → Trivy scan
push ghcr.io/.../railbook:<git SHA>"]
  image --> deploy["deploy job on YOUR laptop
(self-hosted runner railbook-laptop,
least-privilege account github-deployer, 24 h token)"]
  deploy --> helm["helm upgrade --set image.tag=<SHA>
= new numbered release"]
  helm --> roll["Rolling update: start 1 new pod,
wait until Ready, remove 1 old pod, repeat
(never below 2 ready)"]
  roll --> setup["Job railbook-setup
(Helm hook after upgrade)"]
  setup --> ok{"Pods Ready and
Job succeeded?"}
  ok -- no --> rollback["Helm rolls back to the
previous release by itself"]
  ok -- yes --> smoke["Smoke test through Kong:
/ and /stations return 200"]
  smoke --> live(["New version live"])

6. When things fail: what Kubernetes does on its own

Kubernetes keeps comparing "what should run" with "what runs" and fixes the difference. The last branch is the real outage of 2026-10-25, which this loop could not fix by itself (fixed in the app and chart on 2026-10-29).

flowchart TD
  start(["Something goes wrong
with an API pod"]) --> q1{"What kind of failure?"}

  q1 -->|"process crashes"| c1["Container exits"] --> r1["kubelet restarts it
(restart count +1)"]
  q1 -->|"pod deleted / node lost"| c2["Fewer pods than replicas: 2"] --> r2["ReplicaSet creates a new pod
(tested: 0 failed requests)"]
  q1 -->|"hangs: /healthz stops answering"| c3["Liveness probe fails 3 times"] --> r1
  q1 -->|"can't reach the database:
/readyz returns 503"| c4["Readiness probe fails"] --> r4["Pod removed from the Service:
Kong stops sending it traffic"]
  r4 --> q2{"Does the database
come back?"}
  q2 -->|"yes (Postgres restarted)"| back["/readyz OK again → traffic resumes"]
  q2 -->|"no: the app's own DB user
was deleted"| stuck["Stuck: pod alive but never ready
→ site returns 503"]

  stuck --> why["Why (2026-10-25): init container and sidecar each got
their own DB user. The app used the init's,
only the sidecar's was renewed → Vault dropped
the app's user after 1 h"]
  why --> fix["Fixed 2026-10-29: agent cache (one lease per pod)
+ app reads db.json on every new connection"]
  why -.-> alerts["Alerts: KubePodNotReady fired; RailBookApiDown
did not (metrics still scraped) — now also fires on
0 Ready replicas. No receiver is configured to notify anyone"]

7. Every port, and where it lives

A port number only means something together with where it is. The same number can appear in several layers and mean different things: 8000 is Kong's proxy inside its pod, the API inside its pod, and Splunk's web UI on the laptop.

LayerWhat it isAddress rangeReachable from
LaptopA port on your machine, published by Docker127.0.0.1Only your laptop (not Wi-Fi, not the internet)
ContainerA Docker container running directly on the laptop, outside Kubernetes172.19.0.x (Docker network kind)Containers on that network; the laptop only where published
NodeA port opened on the kind node container itself (by Kubernetes, or a host-network pod)172.19.0.2The Docker network; the laptop only where published
ServiceA stable virtual address with a DNS name, in front of pods that come and go10.96.x.xInside the cluster only
PodWhere a program actually listens. Changes IP each time the pod is replaced10.244.0.xInside the cluster only
